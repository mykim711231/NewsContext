# NewsContext 연구 접근과 분석 개념

작성일: 2026-11-13. 경제뉴스만 사용하는 분석 설계이며 구현·성능 검증 결과가 아닙니다. 업무 단계는 Crawler → Part A → Part B를 유지하고, 아래 여섯 축은 생성된 지식을 분석하는 관점으로 적용합니다.

이 문서는 리서치 방법론 관점의 설계 검토를 반영합니다. 문서를 검토하는 전문 에이전트와 앱 실행 중 뉴스 분석을 수행하는 Agent는 구분합니다. 전문가 검색·역할 카탈로그·전문가 팀 편성 기능은 현재 앱 요구사항에 포함하지 않습니다.

## 1. 프로젝트 정의

NewsContext는 경제뉴스에 표현된 이슈·사건·기업·업종·시장 반응을 시간과 근거를 가진 주장으로 구조화하고, 사건의 흐름·전후 맥락·규칙상 도출·잠재 연결·보도된 원인 설명을 탐색하는 플랫폼입니다.

최종 산출물은 [심층 리서치 보고서](report-output.md)입니다. 아래 여섯 분석 축은 보고서의 시간·맥락·도출·가설·인과 설명·분석 한계를 구성합니다. 로컬 Agent가 근거를 선택·보완해 작성하고 공개 데모는 검토된 결과만 제공합니다.

경제뉴스만으로 추출한 시장 반응은 기사에 보도된 내용입니다. 실제 가격 변화를 독립 검증하거나 개입 효과를 계산하지 않습니다. “시장 변화를 인식”한다는 표현의 범위를 이 보도 기반 분석으로 고정합니다.

## 2. 여섯 연구 축

| 연구 분야 | 프로젝트 분석 질문 | 적용 방법 | 결과와 근거 수준 | 우선순위 |
|---|---|---|---|---|
| Temporal Analysis | 이슈·보도된 반응이 언제 어떻게 달라졌는가? | 시간 속성을 가진 KG, Event Timeline, 버전 비교 | 사건·기사·수집 시각을 구분한 타임라인 | MVP |
| Context Awareness | 사건 전후 같은 대상·이슈에 어떤 보도가 연결되는가? | 기간 필터·SQL 그래프 경로 조회(1~2 hop)·근거 묶음; 후속 커뮤니티 탐색·그래프 기반 RAG | 관련 맥락과 원문 목록 | MVP, 확장 |
| Logical Reasoning | 근거가 연결된 주장과 승인된 규칙에서 무엇을 도출할 수 있는가? | 명시적 규칙·기호 추론; 후속 Rule Mining | 규칙 ID·입력 주장·유도 경로가 있는 도출 결과 | 2차 |
| Knowledge Discovery | 아직 검증되지 않은 연결 후보는 무엇인가? | 제한된 multi-hop 경로·공통 이웃·후속 구조 기반 Link Prediction | 후보와 경로·점수·검토 상태 | 2차 |
| Causal Relation Analysis | 기사에서 어떤 사건을 다른 사건의 배경·원인으로 설명하는가? | Event Causality Extraction, 주장 귀속·인용 검증 | 보도된 원인 설명과 발화자·기사 근거 | MVP |
| Causal Inference | X에 개입하면 Y가 얼마나 달라지는가? | 식별 가정·SCM·개입/관측 데이터; Causal Discovery는 가설 구조 탐색 | 현재 데이터만으로 효과를 추정하지 않음 | 후속 연구 |

위 방법들은 후보이며 모두 MVP 필수 패키지가 아닙니다. 특히 Rule Mining과 Link Prediction은 고정 규칙·경로 탐색이 검증된 이후 별도 데이터와 평가로 도입합니다.

## 3. Temporal Analysis: 시간 관계와 사건 흐름

최소 시간 필드는 `published_at`, `event_time_start/end`, `reaction_time_start/end`, `collected_at`, `available_at` 및 시간 정밀도·정규화 근거입니다. 알려지지 않은 시각은 null로 두며 기사 발행 시각을 사건일로 대체하지 않습니다.

“전날 하락했지만 오늘 반등할 전망”에서 관측된 하락과 전망인 반등을 분리합니다. `BEFORE`, `AFTER`, `OVERLAPS`는 시간 구간이 판단을 허용할 때만 생성하고, 순서만으로 원인을 생성하지 않습니다. 분 단위 정보가 없는 두 사건의 세부 순서를 임의로 정하지 않습니다.

과거 시점 재현 분석은 그 시점까지 시스템이 실제 수집·사용 가능했던 원문 버전만 사용합니다. 나중 정정된 기사와 추출 버전을 과거 시점에 이미 알았던 것처럼 사용하는 것을 방지합니다. 처음 구축하며 과거 기사를 수집한 경우에는 당시 시스템이 보유한 자료가 아니므로 ‘현재 수집한 과거 보도에 대한 회고 분석’으로 표시합니다. 분석 대상 기간·발행 기준 시점·시스템 가용 기준 시점을 각각 기록합니다. 뉴스량 변화는 보도 빈도이며 실제 시장 영향 크기의 지표로 단정하지 않습니다.

검증: 상대 날짜·휴일 표현·시간 미상·정정·사건 시점과 발행 시점의 차이를 포함한 정답 타임라인을 비교합니다.

## 4. Context Awareness: 관련 근거를 묶는 검색

MVP는 이슈/대상 ID·키워드·별칭으로 시작 노드를 찾고 날짜 범위와 제한된 1~2 hop 경로로 관련 기사·주장을 조회합니다. 같은 기간에 있다는 이유만으로 관련성을 확정하지 않고 공유 대상·사건·명시 관계를 표시합니다.

기본은 구조화 검색·고정 SQL 그래프 조회이며 필요한 구간에는 임베딩을 조건부 허용합니다. 스키마·개체·기사 후보 검색의 pgvector 결과는 동일 snapshot·시간 범위·모델 profile로 제한합니다. GraphRAG의 원형 local search는 embedding 입력을 사용하고 global community map/reduce는 별도 경로이므로 둘을 구분합니다. 패키지 전체를 도입하기보다 ToG식 경로 탐색과 근거 묶음 종합을 LangGraph로 재구성합니다. [GraphRAG 개요](https://microsoft.github.io/graphrag/), [참조 구현 계획](reference-implementation-plan.md), [임베딩 설계](embedding-retrieval.md)

Community Detection은 촘촘히 연결된 보도 주제를 묶는 보조 기능입니다. 군집은 실제 산업 분류·인과 집단의 정답이 아닙니다. 그래프 DB의 GDS 프로시저를 쓰지 않고 snapshot 범위 부분 그래프를 PostgreSQL에서 읽어 Python(예: networkx)으로 알고리즘을 적용합니다. 데이터 충분성과 평가가 확보되면 Louvain 등의 방법을 비교합니다. [Neo4j Louvain 문서](https://neo4j.com/docs/graph-data-science/current/algorithms/louvain/)

공개 Render 데모(향후)는 사전 계산한 근거·맥락 결과를 조회합니다. 방문자 요청마다 LLM을 호출하지 않으며 실시간 Agent 질의응답은 공개 MVP 범위가 아닙니다.

검증: 고정 질문별 관련 기사 precision/recall, 기간 밖 자료 유입, 원문 근거와 요약의 정합성을 확인합니다.

## 5. Logical Reasoning: 규칙을 설명할 수 있는 도출

초기에는 승인된 명시 규칙을 Python 함수 또는 고정 SQL로 구현합니다. 예를 들어 “기업이 업종에 속하고 해당 기업이 사건의 참여자라면 그 사건은 업종 맥락 후보가 된다”는 규칙을 적용할 수 있습니다. 이 결론은 업종 전체가 영향을 받았다는 사실이 아닙니다.

각 결과는 `rule_id`, `rule_version`, `premise_claim_ids`, `valid_time`, `derived_at`, `status`를 보관합니다. 입력 근거 철회·정정 시 의존 결과를 재계산합니다. 정보가 없다는 사실을 부정의 증거로 사용하지 않습니다.

Rule Mining이 제안한 규칙은 가설로 저장하며 자동 운영 규칙으로 승격하지 않습니다. 사람이 의미·적용 조건·반례를 검토한 뒤 별도 승인합니다. 지식 불완전성과 전망/부정/불확실성이 전파되도록 합니다.

검증: 도출 가능한 정답과 금지된 도출·반례·근거 철회 시 결과 무효화를 확인합니다.

## 6. Knowledge Discovery: 경로와 연결 후보

Multi-hop은 이미 존재하는 관계를 순회하여 연결 경로를 찾는 것이고, Link Prediction은 새 관계가 성립할 가능성을 추정하는 별도 과제입니다. 둘을 같은 기능으로 표시하지 않습니다.

임베딩 없이 공통 이웃·Jaccard 등 구조 점수로 후보를 정렬할 수 있지만, 대상 관계별로 의미가 다르므로 점수를 확률로 표시하지 않습니다. 같은 기사에 자주 나온다는 사실만으로 기업 간 거래나 인과 관계를 생성하지 않습니다. 타입·시간·중복 보도를 필터링합니다.

후보에는 `candidate_relation`, `path_ids`, `method_version`, `score`, `review_status`를 기록하고 근거가 연결된 보도 주장 그래프와 분리합니다. 평가에는 과거 정보로 미래에 확인된 연결을 찾는 시간 분할과 명확한 음성/미확인 표본 정책이 필요합니다. 미관측 관계를 모두 거짓 정답으로 간주하지 않습니다. 현재 보도만으로 후보의 현실적 진위를 확인할 수 없으면 ‘미확인’으로 남기고 정답인 것처럼 성능을 계산하지 않습니다.

검증: 상위 후보의 사람 검토 precision@k, 경로 설명 가능성, 시간 누수·과잉 연결을 확인합니다.

## 7. Causal Relation Analysis: 기사에 귀속된 원인 설명

Part A에서 원인 사건·결과 사건·표현 구간·발화자·양태·부정 여부를 추출·검증하고, Part B는 확정된 KG snapshot의 해당 주장을 비교·설명합니다. 관계 이름은 `REPORTED_CAUSE`처럼 보도 귀속을 명시하고 단순한 `CAUSES`로 실제 인과 사실을 확정하지 않습니다.

“A 영향으로 B가 하락했다는 분석”에는 분석 주체가 있을 수 있습니다. 원문에서 언론사 설명·인용 전문가 설명을 구별하고, “A 때문은 아니다”·“A가 B를 초래할 수 있다”는 부정과 가능성으로 보존합니다. 수치·사건·방향마다 근거 구간을 연결합니다.

여러 기사가 같은 설명을 반복해도 독립 검증된 원인이 되지 않습니다. A→B와 B→C가 각각 보도되었다고 A→C의 인과효과를 생성하지 않습니다. 이런 경로는 맥락 탐색 대상으로만 노출합니다.

검증: 원인/결과 방향·주체·전망·부정·근거 의미 일치의 정답 평가를 수행합니다.

## 8. Causal Inference: 현재 범위와 연구 확장

인과추론은 기사에 나온 원인을 추출하는 것과 다른 문제입니다. 개입 효과를 계산하려면 처리·결과·교란 요인·분석 단위·시간 범위와 식별 가정을 정의해야 합니다. Causal Discovery가 제안하는 구조도 그 자체로 효과 식별을 보장하지 않습니다. [Pearl, Causal inference in statistics](https://ftp.cs.ucla.edu/pub/stat_ser/r350.pdf)

뉴스만 수집하는 현재 범위에서는 실제 단기 가격 반응의 개입 효과를 추정할 근거가 부족합니다. 향후 시장 결과·노출·대조 자료를 추가하고 연구 설계를 정한 뒤 별도 과제로 수행합니다. 현재 화면에 “정책 때문에 주가가 몇 % 변했다”는 수치를 생성하지 않습니다.

## 9. 데이터의 근거 수준과 저장 계약

분석 결과에는 다음 네 범주를 구분합니다. 이는 UI의 한 필드가 모든 의미를 대신하는 것이 아니라 저장·검토·조회에서 유지해야 할 계약입니다.

| 범주 | 의미 | 필수 추적 |
|---|---|---|
| reported | 기사에서 추출한 주장 | 원문 버전·근거·발화자·양태 |
| derived | 승인 규칙으로 도출한 결과 | 규칙·입력 주장·의존 관계 |
| hypothesis | 연결 후보·Agent 제안 | 탐색 경로·방법·점수·검토 상태 |
| causal_effect | 식별된 개입 효과 | 현재 미지원; 향후 데이터·가정·추정법 필요 |

기사의 주장 자체가 진실로 독립 검증되었다는 뜻은 아닙니다. 승인도 출력 계약과 근거의 적합성을 승인하는 것이며 외부 현실의 진위를 보증하지 않습니다. 시스템은 원문에 귀속된 주장과 시스템이 도출한 결과를 나눠 제시합니다.

## 10. 3단계 파이프라인 및 Agent 접근

Crawler는 함수 파이프라인으로 고정하고 원문·시간·버전을 수집합니다. **Part A는 LLM을 활용한 온톨로지 설계와 KG 구축·검증 단계**입니다. 질문 유형·범위·온톨로지·근거·평가의 분석 계약을 승인한 뒤 기사에서 개체·사건·주장을 추출하고 근거 검증·정합화·적재를 수행하여 인계 가능한 KG snapshot을 발행합니다. **Part B는 Part A의 KG를 읽어 근거를 탐색·비교하고 심층 보고서를 작성·검증·공개하는 단계**입니다. Part B가 KG 원문 추출이나 적재를 수행하지 않습니다. 보고서는 Part B 산출물이며 네 번째 업무 단계로 추가하지 않습니다.

### Part A → Part B 인계 계약

| Part A에서 확정할 사항 | Part B에서 확인·기록할 사항 |
|---|---|
| 지원 질문 유형·여섯 축별 지원 상태·미지원 범위 | 개별 연구 질문이 지원 범위 안인지 판정 |
| 기업·업종·사건·주장·시간·양태·관계 스키마 | ontology_version과 analysis_contract_version 고정 |
| 추출·근거 검증·정합화·적재가 완료된 KG snapshot | kg_snapshot_id·manifest_hash·기사/주장/근거 ID 목록 고정 |
| 관측 보도/전망/해석·reported/derived/hypothesis 기준 | 각 주요 주장에 분류·근거·귀속 부여 |
| 포함/제외·중복/전재·정정·시간 기준과 snapshot의 원문 manifest | snapshot 안에서 선택한 근거·제외 이유·자료 부족 기록 |
| 절별 질문·필수 근거·상충 보도와 반례 점검 항목 | 절별 답변 상태·사용 근거·반례 탐색 이력 |
| 허용 조회 도구·검색 범위·호출/시간/토큰 상한 | 실제 도구 호출·탐색 경로·사용량·중단 사유 |
| 자동 검사·사람 검토·공개 차단 기준 | 검사 결과·검토 대상 해시·공개 결정 |

Part A는 표본 기사로 계약의 표현 가능성과 반례를 확인한 뒤 승인 버전을 발행하고, 이를 사용해 실제 대상 원문의 KG를 구축합니다. 온톨로지 승인만 있고 KG 구축·검증이 완료되지 않았다면 인계 완료가 아닙니다. snapshot manifest에는 분석 계약·온톨로지 버전, 원문 버전/해시, 주장·근거·정합화·적재 버전 및 검증 결과를 묶습니다. DB의 물리 snapshot 기능을 가정하는 것이 아니라, 앱이 발행하는 불변 데이터 버전/manifest입니다.

개별 보고서의 질문·대상·기간은 Part B의 연구 브리프로 받고, 지원되지 않는 질문이나 KG 부족은 범위 축소 또는 Part A 보완 요청으로 돌립니다. 보완 결과는 새 kg_snapshot_id로 발행하고 Part B는 새 manifest를 고정한 별도 실행을 시작합니다. 기존 보고서 실행 중 입력 KG를 조용히 바꾸지 않습니다. 문서 개정 자체를 앱의 자동 전문가 편성 기능으로 해석하지 않습니다.

Agent를 적용할 경우 Part A에는 표본 조회·스키마 검증·구조화 추출·반례 확인 도구를, Part B에는 고정 snapshot의 기간별 조회·개체 검색·경로 조회·원문 근거 대조 도구를 제공합니다. Part B의 근거 대조는 보고서 인용 검증이며 KG의 주장 수정·추출·적재가 아닙니다. 모델이 도구와 추가 탐색 필요성을 선택하는 부분만 Agent로 정의합니다. 고정 함수 순서를 그대로 실행하는 구간은 워크플로입니다. MVP는 소수의 실행 Agent와 결정적 검증 함수로 시작하며 전문가 수나 병렬 호출 수를 품질로 간주하지 않습니다.

```text
사용자 분석 질문
  → Part A의 분석 계약·온톨로지·KG snapshot 선택 및 범위 확인
  → Part B Agent가 허용 읽기 도구 선택 (시간/경로/근거 조회)
  → 결과 검증
  → 정보 충분: reported/derived/hypothesis를 구분해 결과 생성
  → 정보 부족: snapshot 내 추가 조회 또는 Part A 보완 요청·확인 불가 반환
```

도구·조회 횟수·기간·hop·토큰·총 시간을 제한합니다. 삭제·승인·최종 적재·백업 복원은 명시적 프로그램 함수와 관리자 권한이 제어합니다. Agent가 임의 SQL·운영 스키마 변경을 실행하지 않습니다. 로컬에서 생성·검토한 분석 결과만 공개 데모에 제공합니다. 본 문서는 Agent 구현을 완료했다는 의미가 아닙니다.

## 11. 구현 순서와 시연

논문별 학습 순서·적용 노드·실험·도입 조건은 [참조 구현 계획](reference-implementation-plan.md)으로 추적합니다. Temporal/Event 모델은 EventKG, 보고서 맥락/경로는 GraphRAG·ToG, 보도 인과 추출은 Causal KG from News를 참조합니다. AnoT·BOCPD·TLogic는 선택적 탐색 실험, TGB·MIRAI는 과제에 맞춘 시간 분할/도구 평가 참조, 시계열 인과추론·Tigramite는 추가 수치 데이터가 필요한 보류 항목입니다. 논문 구현과 동일한 과제/데이터가 아니면 원형 재현으로 표현하지 않습니다.

MVP는 시간·맥락·보도된 원인 설명의 세 기능부터 구현합니다. 다음으로 승인된 규칙 추론과 연결 후보 탐색을 추가합니다. Community Detection·Rule Mining·Link Prediction은 표본과 정답 평가가 확보된 후 도입합니다. 인과추론은 별도 연구 확장으로 표시합니다.

가상 시연 흐름은 “수출 규제 이슈 선택 → 관련 기업/업종 기사 타임라인 → 반응 보도·전망 비교 → 기사에서 제시한 원인 설명 → 각 원문 근거 확인 → 추가 연결 후보 검토”입니다. 후보·보도·규칙 도출을 다른 표시로 구분하고 불명확한 시간과 부정 표현을 함께 보여줍니다.

포트폴리오의 주장은 “여섯 분야를 모두 완성했다”가 아니라, 여섯 관점을 구분한 설계와 구현된 범위·평가 결과입니다. 각 기능의 실패 사례·시간 누수 방지·근거 추적·복구 가능성을 함께 제시합니다.

## 12. 연구 평가와 해석 한계

정답은 세계의 실제 시장 상태가 아니라 **주어진 기사 집합에서 무엇이 어떻게 보도되었는지**에 대해 작성합니다. 기사에 없는 사실을 찾지 못한 것은 추출 누락으로 계산하지 않습니다. 검토자가 원인·전망·관측·근거 범위에 동의하지 않으면 불일치 유형을 남기고 판정 규칙을 먼저 수정합니다.

평가 단위는 추출 주장·검색 결과·타임라인·보고서로 나눕니다. 주장별 precision/recall, 검색 근거 관련성, 사건 순서 오류, 보고서 질문 충족·근거 지지·상충 포괄을 따로 측정합니다. 하나의 ‘리서치 정확도’ 수치로 합치지 않습니다. 동일 사건의 후속 기사·정정·전재가 개발용과 보류용에 섞이지 않도록 사건 단위로 분리하고 분할 manifest를 고정합니다.

실험은 최소한 ‘기사 목록의 단순 요약’과 ‘시간·맥락·근거 계약을 사용하는 보고서’를 같은 입력·모델·예산에서 비교합니다. Agent의 추가 탐색 효과는 탐색 없는 고정 검색과 비교합니다. 모델의 자기평가는 보조이며 주요 결과는 사람이 원문과 대조합니다. 비교 실험을 수행하기 전에는 품질 향상을 달성했다고 표현하지 않습니다.
