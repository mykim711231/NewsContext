# 2년·3개 신문사 뉴스의 예상 성과와 규모 검증 계획

상태: 수집·임베딩 도입 전 타당성 검토. 실제 기사 건수·수집 성공률·처리 성능·비용을 측정하지 않았습니다. 아래 수치는 용량/시간 시나리오의 가정이며 예측 결과가 아닙니다.

## 1. 검토할 데이터와 결정 순서

대상 후보는 네이버에 게재된 매일경제(009)·서울경제(011)·한국경제(015)의 2년치 기사입니다. 정확한 시작/종료일·포함 섹션·본문 보존/공개 범위는 첫 수집 설정에서 확정합니다. 3개 신문사가 발행한 기사 전체와 연구 대상 경제 이슈 기사는 구분합니다.

순서는 **수집 가능성·표본 품질 확인 → 임베딩 없는 Part A/B 결과 확인 → 실패 원인 분석 → 필요 구간만 임베딩 비교 → 전체 확대 여부 결정**입니다. 임베딩은 허용된 선택지이며 현재 필수 구현·기본 활성화가 아닙니다.

2년치가 있어도 실제 가격 변화·시장 개입 효과를 독립 측정할 수는 없습니다. 기대 성과는 이슈 타임라인·보도 반응/전망 구분·매체 간 상충 비교·기사에 귀속된 인과 설명·근거 기반 심층 보고서입니다. 기사 수 증가가 품질 개선을 자동 보장하지 않습니다.

## 2. 규모 시나리오

2년을 계산 편의상 730일로 두며 실제 날짜의 윤일에 따라 달라집니다. 기사 수는 `3개 매체 × 날짜 수 × 매체당 일평균 기사 수`로 추산합니다.

| 가정: 매체당 하루 기사 | 730일·3매체 기사 수 | 본문 20KB/기사일 때 payload | 본문 요청당 3초 순차 수집의 단순 누적 시간 |
|---|---:|---:|---:|
| 100건 | 219,000건 | 4.38GB | 약 7.6일 |
| 300건 | 657,000건 | 13.14GB | 약 22.8일 |
| 500건 | 1,095,000건 | 21.90GB | 약 38.0일 |

20KB는 UTF-8 본문 크기의 예시입니다. HTML·제목·정정 버전·DB 행·인덱스·추출 결과·checkpoint·백업·벡터 공간은 제외했습니다. 수집 시간도 목록 요청·서버 응답·재시도·실패 복구·중단 시간을 제외한 단순 산술값이며 완료 일정으로 사용하지 않습니다. 3초는 참조 크롤러의 초기 설정이지 사이트가 허용한 보장 속도가 아닙니다.

이 평균들은 네이버의 실제 기사량을 측정한 값이 아닙니다. 선택 섹션·주말·전재·중복·접근 가능한 이력에 따라 실제량이 달라집니다.

## 3. 무료 저장소 적합성

현재 공식 Supabase Free 제공 DB 크기는 500MB입니다. [Supabase](https://supabase.com/pricing) (2026-11-17 결정으로 그래프도 PostgreSQL 테이블에 두므로 공개 데모의 그래프 행도 이 500MB 안에 들어가야 합니다. AuraDB는 사용하지 않습니다.)

위 첫 시나리오만으로도 원문 payload가 Supabase Free 제공량을 크게 넘습니다. 기사당 Document 노드 한 개만 해도 219,000행이고 Claim·Evidence·Event·Entity 노드·관계 행이 추가됩니다. 따라서 **2년 전량을 무료 DB에 적재 가능하다고 확정하지 않습니다.** 실제 표본의 byte·노드/관계 행·checkpoint 증가량으로 상한을 계산합니다.

확대 시 대안은 전체 수집 원본을 로컬 영속 archive와 별도 사본에 보존하고, Supabase에는 이슈별 선별 분석 집합과 공개 보고서/근거를 올리는 방식입니다. 또는 저장 요금제 변경을 검토합니다. 이는 측정 후 선택할 설계 대안이며 아직 archive backend나 유료 전환을 구현·확정한 것이 아닙니다. 이후 §8 결정(2026-11-13)으로 MVP는 로컬 PostgreSQL(그래프 테이블 포함, 2026-11-17)을 정본으로 쓰며, 무료 DB(Supabase)에는 공개 데모(향후)에서 **선별된 활성 분석 집합**만 export합니다.

원문을 로컬 archive로 분리하는 대안을 채택하면 파일 manifest·해시·경로·원문 복구·선별 적재 계보와 archive 자체 백업을 별도로 설계해야 합니다. PostgreSQL dump가 로컬 파일 원본도 백업한다는 가정은 금지합니다. 공개 보고서에 필요한 인용과 불변 원문 버전은 로컬 PC 종료 중에도 검증·열람 가능한 범위로 보존해야 합니다.

## 4. 수집 가능성 검증

2년 전체 일괄 실행 전에 시기별 표본 날짜를 뽑습니다. 각 분기·매체·평일/휴일을 포함해 목록 페이지 이력·URL 형식·본문·발행/수정 시각·정정·중복을 확인합니다. 첫 표본의 규모는 수집 허용 범위를 확인한 뒤 제한합니다.

기록 항목은 요청/성공/403/429/본문 누락 건수, 중복 제거 전후 기사량, 날짜별 목록 종료, 링크 재방문, 요청 간격, 원문 byte, 출처별 누락과 수집 범위입니다. 과거 목록이 실제로 2년 전체를 제공하는지와 본문 접근이 되는지는 아직 검증하지 않았습니다. robots·이용 조건·기사 사용 허용 범위도 확인해야 합니다. 이번 검토에서는 robots.txt를 도구로 열지 못했으며 허용/금지 어느 쪽으로도 확정하지 않습니다.

403/429 또는 반복 빈 본문을 정상 완료로 표시하지 않습니다. 차단을 우회하지 않고 중단·재개 가능한 범위별 작업으로 처리합니다. 목록 수집 완료와 본문 보관 완료를 분리하며 수집 건수만으로 전체 coverage를 주장하지 않습니다.

## 5. 임베딩 전 성과 실험

### 단계 1: 작은 종단 표본

이슈 2~3개·기사 약 100~300건을 초기 후보로 두고 실제 허용 자료에서 정합니다. 서로 다른 매체·관측/전망·상충·부정·정정 사례를 포함합니다. 정답 표본 20~40건을 사람이 검토하고 타임라인·이슈/대상·근거 span을 고정합니다. 이 숫자는 실험 설계 초안이며 이미 수집된 자료 수가 아닙니다.

Crawler→Part A 온톨로지/KG→Part B 보고서 1~3편을 먼저 완성합니다. 키워드·별칭·구조화 필터·고정 SQL 그래프 조회만 사용하고 embedding 모델은 설치·호출하지 않습니다. 같은 corpus로 단순 기사 요약과 근거 그래프 보고서를 비교합니다.

### 단계 2: 기간·규모 확대

여러 시기의 선택 이슈와 기사 수천 건 규모로 확대하되 DB 실측 잔여 공간과 적재량이 허용하는 범위에서 진행합니다. 전체 2년 전량 LLM 추출을 먼저 실행하지 않습니다. 보고서 질문과 관련된 기사 후보를 필터하고 누락 검사를 수행합니다. 관련성을 제목 키워드 하나로만 결정하지 않고 본문·별칭·사람 표본을 함께 확인합니다.

기사당 입력/출력 토큰·모델 비용 추정·재시도·검토 시간·KG 노드/관계·checkpoint 공간을 측정합니다. 전체 예상 비용은 `선별 기사 수 × 기사당 실측 비용 + ontology/보고서/재처리 비용`으로 계산하며 모델 단가와 실행 시점을 기록합니다.

### 단계 3: 2년치 활용 구조 결정

표본 수집 coverage·활성 분석 집합 품질·처리/보관 예산을 확인한 후 전체 수집 또는 범위 축소를 결정합니다. 2년이라는 기간은 장기 맥락과 여러 이슈 비교에 쓰고 모든 기사·모든 관계를 하나의 거대한 KG에 넣는 것을 목표로 하지 않습니다.

## 6. 먼저 확인할 성과

| 지표 | 확인 질문 |
|---|---|
| 근거 검색 recall@k | 정답 근거를 키워드/별칭/그래프가 찾는가? |
| 추출 precision/recall | 이슈·대상·반응·시간·원인 설명을 정확히 추출하는가? |
| 과잉 병합 | 동명 기업·기간이 다른 사건이 잘못 합쳐지는가? |
| 보고서 주장 지지 | 주요 문장이 연결 근거로 실제 뒷받침되는가? |
| 질문 충족·상충 포괄 | 연구 질문과 반대 보도를 누락하지 않는가? |
| 시간 누수 | cutoff 이후 정정/보도가 과거 분석에 섞이는가? |
| 운영 비용 | 기사·보고서당 비용/시간/검토 시간과 용량은 얼마인가? |

예상 성과는 이 지표를 측정할 수 있는 결과를 만든다는 의미입니다. 현재 성공률·예측 정확도·비용 절감률을 약속하지 않습니다. 3매체만으로 언론 전체·시장 전체를 대표한다고 보지 않고 편향·누락·전재 중복을 보고서 한계에 표시합니다.

## 7. 임베딩 도입/보류 판정

실패를 먼저 분류합니다. 동의어·완곡 표현·관계 정의의 유사 표현 때문에 올바른 근거를 못 찾는다면 embedding 실험 대상입니다. 원문 누락·시간 오류·부정 해석·잘못된 추출 계약·출처 중복은 해당 기능을 수정해야 하며 vector 검색만 추가해 해결됐다고 보지 않습니다.

기준선 corpus·질문·split·LLM·전체 예산을 고정하고 lexical/graph 대비 schema retrieval·entity 후보·report retrieval를 각각 실험합니다. 개선 폭의 최소 기준·비용·용량 상한은 파일럿 이후 보류셋을 보기 전에 기록합니다. 근거 recall/질문 충족이 실질적으로 개선되고 주장 precision·병합·시간 누수 기준이 나빠지지 않는 기능만 채택합니다. 개선이 작거나 저장/비용 부담이 크면 보류합니다.

결정 상태는 baseline_pending → baseline_measured → embedding_experiment_needed 또는 embedding_deferred → experiment_evaluated → selected_feature_enabled/deferred입니다. `EMBEDDING_ENABLED=false`를 유지하고 평가 전 전체 기사 embedding 작업을 만들지 않습니다. 실험 방법은 [임베딩 설계](embedding-retrieval.md), 논문 매핑은 [참조 구현 계획](reference-implementation-plan.md)을 따릅니다.

## 8. 확정: 로컬 본체 / 공개 데모 분리

상태: **방향 확정(2026-11-13)**. 이전 버전은 `archive/2026-11-13_pre-local-public-split/`에 백업했습니다. 확정 대상은 아키텍처 방향이며, 아래 §8.3의 세부 항목과 구현은 아직 미완입니다. 무료 한도·요금은 공식 페이지에서 재확인합니다.

**구현 순서 결정(2026-11-13, 사용자): 로컬 본체에 집중하고 공개 데모는 향후로 미룹니다.** `.env`를 `public_demo`로 설정해 공개 데모를 만드는 시점부터 그 구현(export 단계, Supabase 연결, 읽기 전용 경로)을 시작합니다. 그 전까지 아래 공개 데모·export 내용은 설계 메모이며 MVP 범위에 넣지 않습니다. 단, 로컬 코드에서 공개 분리를 막지 않도록 `APP_MODE` 분기와 본문 비공개 원칙만 유지합니다.

§3의 "무료 DB 기반 MVP"와 "로컬 archive 대안"은 이 분리안으로 대체·구체화됩니다. 클라우드 벤더 교체는 하지 않으며, 용량 문제는 저장 계층 분리로 해결합니다.

### 8.1 구분

| 구분 | 로컬(본체) | 공개 데모(포트폴리오) |
|---|---|---|
| 데이터 | 확대 시 2년치 전량 원문 archive | 이슈 2~3개분 선별 기사의 링크·제목·짧은 요약·근거 span |
| 저장소 | PostgreSQL(그래프 테이블 포함), 파일 archive | Supabase Free(그래프 테이블 포함) |
| 역할 | 수집·KG 구축·보고서 생성·성과 측정·재처리 | 결과 열람·그래프 시각화·샘플 보고서 |
| 가용성 | PC 가동 중에만 | 로컬 PC와 무관하게 상시 |

공개 데모에는 기사 본문을 두지 않고 **원문 URL 링크**와 우리가 만든 분석 결과·보고서만 둡니다(2026-11-13 사용자 결정). 위 표의 "짧은 요약·근거 span"은 요약·인용 허용 여부가 정해질 때까지 보류합니다.

### 8.2 설계 원칙

- 로컬과 공개 환경은 `.env`의 연결 문자열 교체만으로 같은 코드가 동작해야 합니다. 로컬 DB 구동 방식(Docker Compose 등)은 새 의존성이므로 설치 전 사용자 승인을 받습니다.
- 파이프라인 마지막에 **공개용 export 단계**를 둡니다. 이슈 단위로 기사·근거·보고서를 선별해 공개 DB에 적재하고, 로컬 기사와의 계보(manifest·해시)를 남깁니다.
- 공개 데모는 로컬 서버에 의존하지 않습니다. 공개 가능한 근거와 불변 원문 버전은 공개 DB만으로 검증·열람되어야 합니다(§3 마지막 문단과 동일 원칙).
- 로컬 archive 백업은 PostgreSQL dump와 별도로 설계합니다. dump가 파일 원본을 포함한다고 가정하지 않습니다.
- export 단계에서 공개 DB의 행·노드 수가 한도 대비 상한을 넘지 않는지 검사합니다.

**공개용 export 초안 (2026-11-13, 미구현):**

- 입력: 로컬에서 승인된 이슈 단위와 ready 상태의 `kg_snapshot_id`, 승인된 보고서 버전.
- 허용 필드(allowlist 방식): 기사 ID·원문 URL·제목·매체·발행 시각·원문 해시, 분석 결과(엔터티·관계·증거 수준·reported/derived/hypothesis), 보고서 본문(우리가 작성한 글). **기사 본문과 본문에서 잘라낸 문장은 기본 제외**합니다. 목록에 없는 필드는 자동으로 빠지도록 하고 새 필드는 명시적으로 추가해야만 나갑니다.
- 근거 표시: 본문 span 대신 원문 URL 링크와 해시·offset 메타데이터만 둡니다. 이에 따라 "공개 DB만으로 근거를 검증"하는 위 원칙은 **원문 링크가 살아 있는 동안 링크로 재확인**하는 수준으로 약해집니다. 링크 소실 시 해당 근거는 검증 불가로 표시합니다(미결정: 짧은 인용 허용 여부).
- 사전 검사(실패 시 중단, 공개 DB 변경 없음): ① 본문 필드 유입 검사 ② 행·노드 수가 상한 이하 ③ 모든 근거가 URL과 해시를 가짐 ④ manifest 일치.
- 기록: export manifest(snapshot ID, 기사 ID 목록, 필드 목록 버전, 항목별 해시, 실행 시각)를 로컬 PostgreSQL에 저장하고 같은 요약을 공개 DB에 둡니다. 재실행은 멱등 키로 중복을 막습니다.
- 철회: 원문 URL이 삭제되거나 정정되면 해당 항목을 공개 DB에서 내리는 철회 절차가 필요합니다(미설계).
